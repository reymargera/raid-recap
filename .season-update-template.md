# Season Update Template

This document outlines the step-by-step process for updating the Raid Recap site for a new WoW season.

> **v2.0** - revised for the current Cloudflare Workers + D1 architecture. See `SEASON-UPDATE-GUIDE.md` → "What Changed Since Last Revision" if comparing against an older season's diff.

## Prerequisites: Information Gathering

Before starting the update, gather the following information (see `.season-update-worksheet.md` for a fillable version):

### Basic Season Information
- [ ] Season Name: `_______________________`
- [ ] Season Number: `_______________________`
- [ ] Season Start Date/Time (UTC): `_______________________`
- [ ] Raid Name: `_______________________`

### Raid Encounters
Create a list of all bosses with their encounter IDs and names:

```
Boss 1: [ID: ____] Name: _______________
Boss 2: [ID: ____] Name: _______________
Boss 3: [ID: ____] Name: _______________
...
```

**How to find encounter IDs:**
- Check WarcraftLogs URLs (e.g., `warcraft-logs.com/zone/reports?zone=38` where 38 is the zone)
- Use WarcraftLogs GraphQL API explorer
- Reference previous season updates in git history (`git log --oneline | grep -i season`)

### Mechanics to Track (for seasonal awards)
For each mechanic you want to track, gather:

```
Mechanic Name: _______________
Boss: _______________
Ability ID(s): _______________
Type: [DPS Loss / Debuff / Buff / Death / Damage Taken]
Stat Key Name: _______________ (camelCase, e.g., 'timesStoodInFire')
Description: _______________
Award Name: _______________ (optional)
Award Description: _______________ (optional)
```

**How to find ability IDs and descriptions:**
- Run `python3 scripts/build_boss_abilities.py <JournalInstanceID>` (see `wow-exports/README.md`) to get every boss's full ability list with names and tooltip text in one pass - this is the fastest way to survey what's available before picking mechanics to track
- From WarcraftLogs: Check the ability in the events/damage tables of a real report
- From in-game combat log

### Boss Abilities (for the Boss Details modal - separate from seasonal awards)
For each boss, optionally gather a broader list of notable abilities (not just the ones becoming awards) with tags for the damage/death breakdown UI:

```
Boss: _______________
  Ability: _______________ | ID: _____ | Tags: [Avoidable/Unavoidable, DoT, AoE, Frontal, Targeted, Mechanic, GroundHazard, LossOfControl, TankBuster, Soak, Ramping]
```

This feeds `boss-abilities.ts` and is independent of the award pipeline - you can build this out incrementally after launch since it only affects the boss-details-modal breakdown, not core stat tracking.

## Step 3: Update Seasonal Stats Keys

**File:** `src/warcraft-logs/model/player-stats.ts`

### Task
1. Add a new seasonal stat keys array (e.g., `TWWSeason[N]StatKeys`) - **keep the old season arrays in the file**, they're harmless and useful as reference
2. Update `SeasonalStatKeys` to reference the new array
3. **Update the loop inside `generateBlankStats()`** - it's hardcoded to a specific season's array (currently `TWWSeason3StatKeys`) and does **not** automatically follow `SeasonalStatKeys`. This is the easiest step to miss.

### Template
```typescript
export const TWWSeason[N]StatKeys = [
    '[statKey1]',  // e.g., 'timesStoodInTrash'
    '[statKey2]',  // e.g., 'timesRolledOver'
    '[statKey3]',  // e.g., 'highRollerUptime'
    // ... add all seasonal mechanics
] as const;

export const SeasonalStatKeys = [...TWWSeason[N]StatKeys];
```

```typescript
export function generateBlankStats(): Stats {
    const seasonalStats: SeasonalStats = {} as SeasonalStats;
    for (const key of TWWSeason[N]StatKeys) {   // <-- update this line
        seasonalStats[key] = 0;
    }
    // ...
}
```

### Stat Key Naming Conventions
- Use camelCase
- Be descriptive but concise
- Common patterns:
  - `times[Action]`: Count of occurrences (e.g., `timesStoodInFire`)
  - `[mechanic]Uptime`: Duration tracked in milliseconds (e.g., `debuffUptime`)
  - `[mechanic]Applications`: Times debuff was applied (e.g., `staticDischargeApplications`)
  - `[mechanic]Deaths` / `[mechanic]Hits` / `[mechanic]Damage`: as appropriate

### Important: This Is a Full Replacement, Not an Append (learned the hard way during Midnight Season 1)

Seasonal stats/awards are **current-season only** - unlike `encounters.ts`. When you swap `SeasonalStatKeys` to the new season's array, the *old* season's award definitions in `awards.ts` immediately fail to type-check (they call `getSeaontalStat('oldKey', ...)` and `oldKey` is no longer part of the `SeasonalStatKey` union). You must actually delete the old season's award objects from `awards.ts` and their entries from `SeasonalAwards`, not just leave them alongside the new ones.

This cascades further than it looks:
1. The old season's GraphQL fragments in `GetReport.ts` (and their extraction code in `log-puller.ts`) become dead - nothing reads that data anymore, so remove them too, don't just leave them fetching unused data.
2. **Watch for now-unused query variables.** If a variable (e.g. `$trashFightIds`, `$skipTrashFights`) was *only* ever referenced inside the fragment you just deleted, the GraphQL query becomes invalid - GraphQL requires every declared operation variable to be used somewhere in the query. This isn't just a `GetReport.ts` fix: it ripples through `client.ts`'s method signature and every call site that passes that variable (`log-puller.ts`, `team-actions.ts`, `process-report-workflow.ts` as of Midnight S1).
3. Run `npx tsc --noEmit` after this step (and again after Step 6/7) to catch all of this - it will surface every orphaned reference precisely.

## Step 4: Create Awards

**File:** `src/app/_config/awards.ts`

### Task
1. Create award objects for each seasonal mechanic
2. Update `SeasonalAwards` array
3. Assign appropriate background images

```typescript
const [awardVariableName]: Award = {
    name: '[Award Title]',

    background: '[season-dir]/[image].webp',
};

    [awardVariableName],
    // ... more awards
];
```

### Award Naming Conventions
- **name**: Short, punchy, often humorous title
- **description**: Clear description of what is being measured
- **supportsAveraging**:
  - `false` for counts (e.g., "Number of times...")
  - `true` for amounts/damage (e.g., "Total damage taken...")

## Step 6: Update GraphQL Queries

**File:** `src/warcraft-logs/queries/GetReport.ts`

### Task
1. Create GraphQL fragments for each mechanic
2. Add fragments to the `GetReport` query (both the spread inside the query body and the `${Fragment}` interpolation list at the bottom)
3. Run `npm run generate` after saving to regenerate types

### Understanding WarcraftLogs Data Types

**Common Query Types:**
- `table(dataType: DamageTaken)`: Damage taken from abilities
- `table(dataType: Debuffs)`: Debuff applications/removals
- `table(dataType: Buffs)`: Buff applications/removals
- `table(dataType: Casts)`: Ability casts
- `table(dataType: Deaths)`: Death events

**Common Filters:**
- `abilityID: [ID]`: Filter by specific ability
- `filterExpression: "..."`: Complex filtering using WCL query language
- `fightIDs: $bossFightIds`: Limit to specific fights

### Fragment Template
```typescript
export const [MechanicName]Fragment = gql`
    fragment [MechanicName]Fragment on Report {
        [queryName]: table(
            fightIDs: $bossFightIds
            dataType: [DataType]
            abilityID: [ABILITY_ID]
        )
    }
`;
```

### Example (current pattern, from Manaforge Omega)
```typescript
export const PlexusAtomizerDeathsFragment = gql`
    fragment PlexusAtomizerDeathsFragment on Report {
        atomizerDeaths: table(
            fightIDs: $bossFightIds
            dataType: Deaths
            abilityID: 1219223
        )
    }
`;
```

Add each new fragment to both places in the `GetReport` query:
```typescript
export const GetReport = gql`
    query getReport(...) {
        bossFights: reportData {
            report(code: $reportCode) {
                ...CoreReportFragment
                ...[NewMechanic]Fragment   // <-- add here
            }
        }
    }
    ${CoreReportFragment}
    ${[NewMechanic]Fragment}   // <-- and here
`;
```

## Step 7: Extract Data from Reports

**File:** `src/app/teams/[id]/log-puller.ts`

### Common Extraction Patterns (using existing helpers)

```typescript
// Count occurrences (e.g., deaths, applications)
const timesScrewed = sumByPlayer(getTableDataEntries(report?.screwedApplications), (d: any) => 1);

// Track uptime/total via 'auras' shape
const highRollerUptime = sumByPlayer(getTableDataAuras(report?.highRollerUptime), (d: any) => d.totalUses);

// Track damage (uses default d.total selector)
const fireDamage = sumByPlayer(getTableDataEntries(report?.fireDamage));

// Track cast count
const bombsCast = sumByPlayer(getTableDataEntries(report?.bombsCast), (d: any) => d.uses);
```

Add each new extraction, then add it to the function's return object (see Step 5.3 for wiring it into `seasonalStats`).

## Step 9: Build the Boss Abilities Map (NEW since v1.0)

**File:** `src/warcraft-logs/data/boss-abilities.ts`

### Task
Replace `BossNames` and `BOSS_ABILITIES` with the new raid's bosses and their notable abilities, tagged for the boss-details-modal's damage/death breakdown. This is independent of the seasonal-award pipeline (Steps 3-7) - it can be built out incrementally after launch since it only affects one UI section.

### Generate the candidate list

1. Set up `wow-exports/` per `wow-exports/README.md` (one-time per season)
2. Find the raid's `JournalInstanceID` (see the README - not the same as the WCL zone ID or per-boss encounter ID)
3. Run:
   ```bash
   python3 scripts/build_boss_abilities.py <JournalInstanceID> --out wow-exports/<raid-name>-abilities.csv
   ```
   This gives every boss's full ability list, already attributed to the correct boss, with real names and tooltip descriptions - ready to skim and tag. Repeat per raid if the tier has more than one.
4. Fill in the `tags` column of the output CSV, then transcribe into the map below.

```typescript
const BossNames = {
    [ENCOUNTER_ID]: '[Boss Name]',
    // ... one per boss
} as const;

export type BossEncounterId = keyof typeof BossNames;

export const BOSS_ABILITIES = new Map<BossEncounterId, BossAbilityInfo[]>([
    [[ENCOUNTER_ID], [ // [Boss Name]
        { guid: [ABILITY_ID], name: '[Ability Name]', tags: [AbilityTag.Avoidable, AbilityTag.AoE] },
        // ...
    ]],
]);
```

## Common Issues and Solutions

### Issue: Ability ID not tracking
- Verify ability ID is correct in WarcraftLogs
- Check if ability has multiple IDs (different ranks/difficulties) - the current Manaforge Omega setup has several abilities registered twice for this reason (e.g. `Antimatter` at both `1243702` and `1243704`)
- Test the query in WarcraftLogs GraphQL explorer

### Issue: Stats showing as 0 or undefined
- Check data extraction mapping (guid vs name)
- Verify field selector matches (total vs totalUses vs count-by-1)
- Add null coalescing (`?? []` / `?? {}`) to prevent undefined errors

### Issue: TypeScript errors
- Regenerate GraphQL types: `npm run generate`
- Check that new stat keys are added to the new season's array AND that `generateBlankStats()`'s loop was updated to match (see Step 3)

### Issue: Awards not displaying
- Check `SeasonalAwards` array includes new awards
- Check background image paths are correct
- Ensure stat key names match between `awards.ts` and `player-stats.ts`

### Issue: Boss Progression card empty or wrong bosses
- `team-stats.ts` and `boss-progression-card.tsx` weren't repointed to the new encounter array (Step 1.5)
